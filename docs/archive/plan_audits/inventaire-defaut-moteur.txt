Plan — Inventaire exhaustif des défauts du moteur GCN-Python

 Contexte

 Le moteur GCN-Python produit des graphes causaux (CIR) depuis des phrases en langage naturel.
 Il prédit 7 types de nœuds et 11 types de relations. L'exploration systématique du code révèle
 3 catégories de défauts : (1) bugs actifs qui produisent des résultats incorrects, (2) champs
 de schéma jamais renseignés (fonctionnalités annoncées mais vides), (3) limitations de design
 qui plafonnent la qualité des prédictions. Toutes les améliorations A–G d'amelioration_v3.txt
 sont déjà implémentées — ce plan couvre ce qui reste réellement défectueux.

 ---

 PRIORITÉ 1 — Bugs actifs (comportement incorrect, à corriger en premier)

 BUG-1 — R-GCN mono-relationnel : W_1..W_{R-1} sans gradient

 Fichier : pipeline/cgnp.py:301-309

 Problème :
 edge_type_idxs_rgcn = np.zeros(len(_edge_pairs_rgcn), dtype=np.int64)
 # commentaire : "types d'arêtes uniformes — type 0 uniquement"
 Toutes les arêtes sont envoyées dans le type 0 (W_0). Les matrices W_1..W_{10} (pour les
 11 types de relations) sont initialisées aléatoirement mais ne reçoivent jamais de gradient.
 L'avantage fondamental du R-GCN — distinguer les types de relations dans le message passing —
 est entièrement perdu. Le modèle se comporte comme un GCN classique sans distinction relationnelle.

 Impact : Le moteur ne peut pas apprendre que cause propage différemment de prevent.
 C'est la limitation la plus grave pour la qualité des représentations enrichies.

 Solution : Remplacer np.zeros(...) par les indices réels des relations :
 edge_type_idxs_rgcn = np.array(
     [edge_types_mp[k] for k in range(len(_edge_pairs_rgcn))],
     dtype=np.int64
 )
 Vérifier que edge_types_mp contient bien des indices dans [0, n_relations).
 Ajouter un test test_rgcn_multirelational_weights_receive_gradient.

 BUG-2 — GAT dropout avant requires_grad → gradients word_embedding incorrects

 Fichier : layer3/gat.py:221-227

 Problème :
 if self.dropout_rate > 0.0 and self.training:
     mask = torch.bernoulli(...)
     H_in = H_in * mask        # nouveau tenseur, masque hors autograd
 H_in.requires_grad_(True)     # H_in post-dropout devient une feuille
 Le masque dropout n'est pas dans le graphe autograd. La rétropropagation retourne le gradient
 par rapport au vecteur post-dropout. Quand cgnp.py utilise ce gradient pour mettre à jour
 word_embedding, les dimensions zeroisées par le dropout reçoivent un gradient non nul.

 Impact : Avec --rgcn-dropout > 0, les gradients remontant vers word_embedding sont
 incorrects. L'entraînement converge mais apprend une mauvaise distribution de gradients.

 Solution :
 H_in.requires_grad_(True)
 if self.dropout_rate > 0.0 and self.training:
     mask = (torch.rand_like(H_in) > self.dropout_rate).float()
     H_in_dropped = H_in * mask / (1.0 - self.dropout_rate)
 else:
     H_in_dropped = H_in
 out = self._gat_forward(H_in_dropped, edge_index, edge_types)
 Ainsi H_in reste la feuille, le masque est dans le graphe, le gradient remontant
 vers H_in est correct (inclut les zeros du masque).

 BUG-4 — confidence=None classée pire que confidence=0.0 dans find_causes/find_effects

 Fichier : verbalizer/instructions.py:204-211

 Problème :
 conf_val = float(conf) if conf is not None else -1.0
 scored.append((level, -conf_val, idx, ...))
 Tri par (level, -conf_val) :
 - confidence=0.0 → -conf_val = 0.0
 - confidence=None → -conf_val = 1.0

 None sort APRÈS 0.0. Sémantiquement, None = "non renseigné" ≠ "zéro confiance".
 Une arête annotée à 0% est prioritaire sur une arête non annotée.

 Impact : Le ranking des causes/effets dans l'interface verbalizer est incorrect.

 Solution :
 conf_val = float(conf) if conf is not None else 0.5  # défaut neutre
 Ou mieux : trier les None en dernier explicitement :
 conf_sort = float(conf) if conf is not None else float('inf')
 scored.append((level, conf_sort, idx, ...))

 BUG-5 — closed-loop forward-only : node_type_probs hors autograd

 Fichier : pipeline/cgnp.py:383-389

 Problème :
 enriched_edge = np.concatenate([
     edge_vec_base,
     enriched[src_i],
     enriched[dst_i],
     node_type_probs[src_i],   # softmax NumPy, hors autograd torch
     node_type_probs[dst_i],
 ])
 node_type_probs est calculé via softmax NumPy. Le gradient de la loss d'arêtes
 ne peut pas remonter vers les prédictions de types de nœuds via ce chemin.
 La "boucle fermée" est en lecture seule côté gradient.

 Impact : L'architecture CIR suppose que les prédictions nœuds influencent les prédictions
 arêtes ET vice-versa. Seul le sens nœud→arête fonctionne.

 Solution : Si torch est disponible dans ce chemin, utiliser torch.softmax avec
 retain_graph=True. Sinon documenter explicitement cette limitation comme un choix de design
 (compromis mémoire/vitesse) et supprimer la mention "closed-loop" de la documentation.

 BUG-6 — analyze_or_skip sans training=False → non-déterminisme en inférence

 Fichier : pipeline/cgnp.py:555-562

 Problème : analyze() bascule training=False avant le forward (lignes 525-536),
 mais analyze_or_skip() appelle forward() directement sans ce basculement.
 Avec --rgcn-dropout > 0, deux appels identiques à analyze_or_skip() sur la même phrase
 peuvent produire des CIRs différents.

 Impact : Inférence non-déterministe. Résultats non reproductibles.

 Solution :
 def analyze_or_skip(self, text, ...):
     was_training = self.training
     self._toggle(self, False)
     try:
         return self.forward(...)
     finally:
         self._toggle(self, was_training)

 BUG-9 — TrainableDecoder.loss_decode gradient non normalisé (single-step)

 Fichier : verbalizer/trainable.py:244-255

 Problème :
 for t in valid:
     total_loss -= log(probs[t])
     d_t = probs.copy(); d_t[t] -= 1.0
     d_logits += d_t          # somme des gradients

 L-1 — causal_graph_similarity : alignement positionnel invalide

 Fichier : evaluation/metrics.py:117-162

 Problème : node_type_acc est calculé en comparant pred_nodes[i] avec gold_nodes[i]
 par position. Si le modèle insère un nœud supplémentaire en position 0, toutes les comparaisons
 suivantes sont décalées. Un UserWarning est émis mais le calcul continue avec un résultat biaisé.

 Impact : node_type_accuracy est sur-estimée quand |pred| ≠ |gold|.

 Solution : Alignement par type + label (matching hongrois ou greedy par cosine des
 embeddings de type). À court terme : retourner NaN si |pred| ≠ |gold| plutôt qu'un score
 biaisé.

 L-3 — TrainableDecoder : objectif invalide (génération de texte depuis embeddings structurels)

 Fichier : training/train.py:740-752, verbalizer/trainable.py

 Problème :

 Le verbalizer a deux modes. Leur objectif est fondamentalement différent :

 ┌─────────────────────────────────────┬────────────────────────────────────────────────────────────────────────┬───────────────────────────────────────────────────┬──────────┐
 │                Mode                 │                            Ce qu'il apprend                            │                       Gold                        │ Valide ? │
 ├─────────────────────────────────────┼────────────────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────┼──────────┤
 │ legacy (TrainableDecoder)           │ Choisir les tokens du texte de surface complet (autoregressif)         │ gold_tokens = tokens de la phrase entière         │ Non      │
 ├─────────────────────────────────────┼────────────────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────┼──────────┤
 │ lexical (LexicalConnectorAssembler) │ Sélectionner le connecteur (car, donc...) pour chaque type de relation │ connector_gold_idx = index dans vocab connecteurs │ Oui      │
 └─────────────────────────────────────┴────────────────────────────────────────────────────────────────────────┴───────────────────────────────────────────────────┴──────────┘

 Note sur ce que le verbalizer produit : dans les deux modes, la sortie est une phrase
 complète. Ex. : X = {clause1="le chat dort", clause2="il est fatigué", lien=cause} →
 Y = "le chat dort car il est fatigué". Les deux moitiés de phrase sont recopiées depuis
 le graphe ; seul le mot de liaison est appris. Ce n'est donc PAS de la génération pure —
 c'est une assemblage avec sélection apprise du connecteur. Le mode legacy apprend le token
 de liaison dans un décodeur autoregressif complet (coûteux, inutilement complexe). Le mode
 lexical apprend directement relation_type → connecteur_idx par une tête de classification
 légère (correct et suffisant).

 Le type causal (cause/enable/prevent) est prédit par le décodeur principal (edge_logits),
 PAS par le verbalizer. Le verbalizer reçoit le type déjà prédit et l'associe à un mot de surface.

 Le mode legacy essaie de reconstruire une phrase de 50+ tokens depuis 2 vecteurs de clauses
 structurels (d=79 ou 128). C'est informatiquement impossible — les vecteurs structurels ne
 contiennent pas l'information lexicale nécessaire pour reconstruire la surface.
 Conséquence : la dec_loss en mode legacy stagne proche de log(|vocab|) et ne converge pas,
 mais est quand même ajoutée à epoch_loss :

 epoch_loss += dec_loss     # pollue la loss principale
 n_samples += 1             # compte comme un sample standard

 Impact :
 1. epoch_loss mélange deux objectifs incompatibles (classification nœuds/arêtes + génération)
 2. La décroissance de la loss principale est masquée par la stagnation du décodeur legacy
 3. Le décodeur legacy n'améliore jamais la qualité des sorties (il est déprécié pour cette raison)

 Solution :
 - En mode legacy : logger dec_loss séparément dans le CSV (epoch_decoder_loss) et
   ne PAS l'ajouter à epoch_loss. Le mode legacy est déprécié — sa loss ne doit pas
   perturber l'entraînement principal.
 - En mode lexical : assembler_loss est déjà séparée (ligne 764-765). Continuer ainsi.
 - Ajouter dans le CSV : epoch_main_loss, epoch_decoder_loss (si mode legacy actif).

 Test : avec mode legacy activé, epoch_loss doit être identique à une run sans
 --verbalize-dir.

 L-4 — Négation analytique française ("ne…pas") non détectée

 Fichier : pipeline/cgnp.py:1182-1184

 Problème : _detect_negation repose sur rep.is_negative (Polarity=Neg UD). La
 négation analytique française ("ne fait pas") dont "pas" n'est pas le root n'est détectée
 que rarement.

 Solution : Compléter la détection par la présence d'un token dépendant avec
 lemma in {"pas", "plus", "jamais", "rien", "guère"} et dep_rel == "advmod" :
 def _detect_negation(src_rep, dst_rep, connector_rep):
     NEG_LEMMAS = {"pas", "plus", "jamais", "rien", "guère", "nullement"}
     for rep in (src_rep, dst_rep):
         if getattr(rep, 'is_negative', False):
             return True
         if any(t.get('lemma') in NEG_LEMMAS and t.get('dep_rel') == 'advmod'
                for t in getattr(rep, 'tokens', [])):
             return True
     return False

 L-8 — Inter-phrases : accumulation sans apprentissage, liaison non apprise

 Fichier : engine.py:308, pipeline/cgnp.py (analyze_batch), verbalizer/instructions.py:114

 Problème :
 Le moteur traite chaque phrase indépendamment. analyze_batch() boucle sur analyze()
 phrase par phrase. add_discourse_block() concatène les CIRs avec des préfixes d'IDs mais
 ne crée aucun lien inter-phrases. Le moteur est incapable de relier une cause dans la phrase 1
 à son effet dans la phrase 2.

 Ce qui ne doit PAS être implémenté : heuristique de coréférence par correspondance de
 lemmes ("si le même lemme root apparaît dans deux phrases, créer une arête"). Ce serait
 de la mémorisation de surface — fragile, non généralisable. La règle de liaison inter-phrases
 doit être apprise depuis les données, pas imposée manuellement.

 Ce que cela implique concrètement :

 1. Nouvelles données : Annoter des paragraphes (2-3 phrases) avec des CIRs unifiés dans
    gcn-datasets. Un CIR de paragraphe = nœuds provenant de plusieurs phrases + arêtes gold
    reliant ces nœuds, y compris des arêtes inter-phrases. Le moteur apprend depuis ces
    exemples quel type d'entité dans la phrase N est lié à quel type dans la phrase N+1.
 2. Pipeline d'entrée : Modifier engine.py pour accepter une liste de phrases comme
    unité d'analyse et construire un seul graphe UD sur le paragraphe entier :
 def analyze_paragraph(self, sentences: list[str]) -> dict:
     # Analyse UD de toutes les phrases → graphe unifié → pipeline R-GCN unique
 3. Entraînement : La loss sur les arêtes inter-phrases apprend au R-GCN les patterns
    de continuité discursive. Aucune règle supplémentaire n'est nécessaire.

 Effort : Élevé (nouvelles annotations + modification pipeline). Prérequis : 200-300
 exemples de paragraphes annotés avec CIRs multi-phrases. Ne pas implémenter de heuristique
 en attendant ces données — laisser analyze_batch() retourner une liste de CIRs disjoints
 est honnête et correct.

 ---

 L-9 — Représentation de clause : 1 token décrit sur 8 (root seul)

 Fichier : layer1/features.py:vectorize_clause(), mode par défaut clause_pooling="root"

 Problème :

 d_clause=79 n'est PAS un problème de sparsité — c'est un QCM à 7 questions sur la clause :
 - nature du mot (UPOS) → 1 case cochée sur 18
 - fonction syntaxique (dep_rel) → 1 case sur 38
 - POS du sujet → 1 case sur 5
 - temps / aspect / mode → 1 case chacun (3 cases)
 - négation, drapeaux → 0 ou 1
   Total : ~6 cases à 1.0, les 73 autres à 0.0. C'est normal et correct par construction.

 Le vrai problème : ce QCM ne décrit que le token root de la clause (ex. le verbe principal).
 Une clause de 8 mots ("le chat fatigué dort depuis hier matin") est réduite à la description
 du seul verbe "dormir". Les 7 autres tokens (sujet, adverbes, modificateurs, contexte temporel)
 sont ignorés.

 Impact :
 - La représentation d'une clause est appauvrie — deux clauses avec le même verbe root mais
   des sujets/objets différents sont encodées de façon identique.
 - Edge F1 stagne : le modèle ne peut pas distinguer "A cause B" de "A' cause B'" si root(A)=root(A').

 Solutions par niveau d'effort :

 Niveau 1 (déjà implémenté) :
 - --clause-pooling mean : mean-pool sur les tokens de contenu (NOUN/VERB/ADJ/PROPN/ADV)
   → ajoute d_emb dimensions depuis word_embedding
 - --subject-object-emb : ajoute explicitement l'embedding du sujet et de l'objet
   → d_effective passe de d_clause+d_emb à d_clause+3×d_emb

 → Test en cours : si le run Phase 1+2 dépasse baseline+0.06/0.08 F1, ce niveau suffit.

 Niveau 2 (non implémenté) :
 - Encoder les tokens de la clause dans l'ordre → BiLSTM ou mini-Transformer
 - Chaque token garde sa représentation séparée, le modèle apprend quoi agréger
 - Plus puissant mais requiert plus de données et modifie l'architecture de l'encodeur

 Niveau 3 (hors contraintes moteur) :
 - Embeddings pré-entraînés contextuels (CamemBERT) → fossé structurel §11
 - Incompatible avec les contraintes : pas de BERT/Transformers dans le moteur

 Plan : Attendre le résultat du run Phase 1+2. Si amélioration insuffisante → implémenter
 le niveau 2 (BiLSTM sur les tokens de clause).

 N-10 — Arêtes backward asymétriques inversées avec même relation

 Fichier : data/loader.py:154-167

 Problème : Quand src_idx > tgt_idx, la clé est inversée en (tgt_idx, src_idx) mais
 la relation est conservée identique. Pour cause(A, B) annoté à l'envers (src=B, tgt=A),
 l'entraînement reçoit cause(A, B) — la direction est corrigée mais potentiellement
 l'intention de l'annotateur était cause(B, A).

 Solution : Utiliser les types inverses RELATION_TYPES_INV pour les arêtes inversées :
 if src_idx > tgt_idx:
     rel_idx_stored = RELATION_TYPES.index(rel) + len(RELATION_TYPES)  # → version _inv
     key = (tgt_idx, src_idx)
 Nécessite une revue de la convention d'annotation dans le dataset.
