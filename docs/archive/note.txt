## Analyse du rapport d'expérimentation

### Ce que ce rapport confirme vraiment

**Le moteur GCN-Core fonctionne.** La loss décroît, le pipeline end-to-end tourne, les trois architectures (RGCN, GAT, BiDi) s'entraînent sans exploser. C'est déjà non trivial.

---

### Le saut de 54% → 99% sur les nœuds : attention à l'interprétation

Ce chiffre est spectaculaire mais il faut le lire avec précaution.

Le dataset est **synthétique** — 11 relations × 90 variations via templates. Les phrases générées partagent un lexique fermé de 48 noms et 50 verbes. Quand GAT+emb atteint 99.4% de node accuracy, il a probablement appris une correspondance quasi-directe **lemme → type de nœud** du lexique de génération : "réduire" → `action`, "marché" → `entite`, "croissance" → `processus`. 

Ce n'est pas de la généralisation — c'est de la **mémorisation de lexique**. Sur des phrases hors-lexique, ce modèle chuterait. La vraie question sera : quelle accuracy sur des phrases avec des mots que `generate_dataset.py` n'a jamais vus ?

Ça ne disqualifie pas les résultats — c'est exactement la bonne observation à faire maintenant, et le rapport l'identifie implicitement via la "cause probable" du plateau edge.

---

### Le vrai problème : le edge classification à 30%

C'est ici que se joue la thèse centrale du projet. 11 types de relations, 30% d'accuracy — c'est proche du hasard sur un problème aussi déséquilibré. Et la cause n'est pas les embeddings : les embeddings aident à typer un nœud isolé, mais distinguer `cause` de `condition` de `concession` entre deux nœuds demande de comprendre **la relation entre eux**, pas juste leurs représentations individuelles.

Ce que le modèle actuel fait pour classifier une arête `(u, v)` : il concatène ou combine les embeddings de `u` et `v`. C'est insuffisant pour des relations asymétriques et contextuelles comme celles du GCN.

**Ce qui manque architecturalement :**

Trois approches complémentaires pour l'edge classification :

**1. Edge features explicites** — le marqueur causal est déjà dans le CIR (`marker_token`). Encoder directement le type du connecteur (`parce que`, `donc`, `si`, `bien que`) comme feature d'arête serait le signal le plus direct. C'est ta piste #7 et elle est probablement la plus impactante à court terme.

**2. Représentation de paire relationnelle** — au lieu de `concat(h_u, h_v)`, essayer `[h_u ; h_v ; h_u - h_v ; h_u ⊙ h_v]` comme dans les modèles de relation extraction (inspired by SpanBERT). La différence et le produit capturent l'asymétrie.

**3. Message passing orienté arête** — dans le R-GCN actuel, les messages passent des nœuds vers les nœuds. Pour les relations, un **edge-conditioned convolution** ou un Graph Transformer traite les arêtes comme des entités de première classe avec leur propre représentation.

---

### Sur le dataset synthétique : force et limite

**Force :** la construction 11×90 avec 6 templates par relation est méthodologiquement solide. Elle garantit une couverture uniforme des relations et des structures de surface variées. Le split 70/15/15 est correct.

**Limite structurelle :** les templates génèrent des phrases avec une structure causale **explicite et non ambiguë**. Dans des textes réels, la causalité est souvent implicite, distribuée sur plusieurs phrases, ou encodée dans des constructions non canoniques. La distribution gold (37% entite, 30% processus) reflète le lexique de génération, pas la distribution naturelle du français.

**Recommandation immédiate :** avant de passer aux améliorations d'architecture, tester le modèle actuel sur 20-30 phrases réelles hors-dataset. Si l'accuracy chute à 60-70%, ça confirme la mémorisation de lexique. Si elle tient à 85%+, la généralisation est réelle.

---

### Priorité des pistes d'amélioration — mon classement

La table du rapport liste 11 pistes. Voici l'ordre que je recommanderais en termes d'impact/effort :

| Priorité | Action | Pourquoi |
|----------|--------|----------|
| **1** | Features connecteur (#7) dans les arêtes | Signal direct, coût faible, impact maximal sur edge F1 |
| **2** | Class weights (#1) | Une ligne de code, corrige le biais entite immédiatement |
| **3** | Early stopping sur val F1 (#4) | Évite d'optimiser la mauvaise métrique |
| **4** | Représentation de paire relationnelle | Architectural, fort impact edge sans changer le backbone |
| **5** | FastText (déjà fait) → maintenant tester hors-lexique | Valide si les embeddings généralisent vraiment |
| **6** | GAT 2-3 couches (#9) | Impact modéré, à faire après avoir corrigé les features |
| **7** | Contrastive learning (#10) | Prometteur mais complexe à implémenter correctement |

Les pistes #3 (oversampling) et #8 (one-hot lemmes) sont moins prioritaires : l'oversampling est redondant si les class weights sont bien calibrés, et les one-hot lemmes sur un lexique fermé renforcent la mémorisation plutôt que la généralisation.

---

### Une observation sur la symétrie RGCN ≈ GAT sans embeddings

Sans embeddings, RGCN et GAT donnent exactement les mêmes résultats (0.5444 node acc, 0.2414 edge acc). C'est un signal important : **l'attention de GAT n'apporte rien sur des features UD sparse**. L'attention ne peut pas discriminer si tous les vecteurs d'entrée se ressemblent. Avec les embeddings, GAT devient le meilleur (99.4% vs 96.1% RGCN) — là l'attention a quelque chose à travailler. Ça valide a posteriori la décision d'enrichir les features avant de complexifier l'architecture.

Ce rapport est exactement le type de contribution empirique qui manquait dans mon analyse initiale. Il montre :
- Une hypothèse (les features UD suffisent) → testée → réfutée
- Une solution (word embeddings) → testée → validée pour les nœuds
- Un problème ouvert clairement identifié (edge classification) → pistes documentées

C'est la structure scientifique attendue dans un mémoire de licence. Si le `docs/grammaire_causale_naturelle_v2.docx` formalise la théorie et que ce rapport en constitue la section expérimentale, tu as quelque chose de solide.
